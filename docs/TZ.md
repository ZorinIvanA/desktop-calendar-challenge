# Техническое задание (ТЗ)

**Проект:** Desktop Calendar — рисование календаря поверх обоев рабочего стола выбранного монитора.
**Статус документа:** v1.0 (кроссплатформенная редакция, замена WPF → Avalonia).
**Дата:** 2026-07-10.

> Этот документ описывает **что** должно быть сделано (требования). Архитектурное **как** — в
> [`SPECIFICATION.md`](./SPECIFICATION.md). Документы согласованы между собой; при изменении одного
> обновляется второй.

---

## 1. Назначение и результат

Приложение в соответствии с настройками пользователя берёт фоновое изображение рабочего стола
указанного монитора, рисует на нём календарь на текущий месяц и устанавливает полученное
изображение в качестве обоев рабочего стола этого монитора. Перерисовка выполняется ежедневно
(через механизм автозапуска в «silent» режиме) и по требованию из интерфейса.

## 2. Платформы

| Платформа | Целевая версия | Степень поддержки |
|---|---|---|
| Windows | 10 (10.0.19041+), 11 | полная |
| Linux (Ubuntu) | 22.04 LTS, 24.04 LTS | функциональная, primary-DE — **GNOME** |

### 2.1. Поддержка окружений рабочего стола (Linux)

Полноценно поддерживается **GNOME** (включая Ubuntu, где он является DE по умолчанию). Архитектура
допускает подключение других DE (KDE Plasma, XFCE, Cinnamon, MATE) как модулей, не меняющих общий
контракт; в данной редакции ТЗ эти backend'ы **не являются обязательными** и помечены
`unimplemented` (см. §10).

### 2.2. Известные ограничения (per-screen)

- **GNOME** исторически хранит единый URI обоев на всю сессию и не имеет встроенного API для
  независимой установки обоев на отдельные мониторы. Это зафиксировано как **known limitation**:
  в GNOME календарь рисуется на общем фоне, реально обновляются только общие обои, календарь
  визуально «прибит» к выбранному монитору за счёт координатной привязки.
- **Windows** поддерживает `IDesktopWallpaper::SetWallpaper(monitorId, …)` — per-monitor
  поддерживается нативно.

## 3. Технологический стек

- **UI-фреймворк:** Avalonia UI 11.x (.NET 8 LTS).
- **Язык:** C# 12.
- **Платформенный код:** P/Invoke и COM для Windows, `gsettings`/dconf/`DBus` для GNOME
  (конкретные механизмы — в SPECIFICATION.md).
- **Сборка:** `dotnet` CLI, solution с проектами под desktop-scenario (Windows-специфичный код
  изолирован через `<RuntimeIdentifier>` и/или `OperatingSystem.IsWindows()`-гварды).

## 4. Функциональные требования

### 4.1. Сценарий 1 — Конфигурирование (интерактивный режим)

При запуске без аргументов открывается графическое окно настроек. Состав разделов:

1. **Целевой монитор.** Визуализация доступных мониторов в том же порядке и с теми же номерами, что
   видит ОС. Пользователь выбирает один монитор, над изображением которого работает приложение.
2. **Расположение календаря.** 8 точек привязки (4 угла + середина каждого ребра). Дополнительное
   поле — отступ от края экрана в пикселях.
3. **Настройки календаря.** См. §4.5.
4. **Общие настройки.** См. §4.7.
5. **Превью.** См. §4.6.

### 4.2. Сценарий 2 — Silent-режим (ежедневное обновление)

При запуске с ключом `-auto` приложение:
- не открывает UI,
- читает настройки с диска,
- обновляет рабочий стол выбранного монитора в соответствии с настройками,
- завершается с кодом `0` при успехе / ненулевым при ошибке (для диагностики через логи/журнал
  планировщика).

### 4.3. Структура календаря

Строка с названием месяца → строка с краткими названиями дней недели (Mo, Tu, We, Th, Fr, Sa, Su) →
таблица дней месяца (6 строк × 7 столбцов достаточно для любого месяца). Недели начинаются с
понедельника. Локаль названий — `en-US` (фиксированная по ТЗ: Mo/Tu/We/…).

### 4.4. Расположение календаря

- 8 точек привязки: `TopLeft`, `TopCenter`, `TopRight`, `CenterLeft`, `CenterRight`,
  `BottomLeft`, `BottomCenter`, `BottomRight`. (Центр экрана в `Center`-точках по одной оси
  ребра/угла.)
- Отступ от края экрана — целое число пикселей (≥ 0). Применяется как расстояние от границы
  прямоугольника календаря до соответствующего края/ребра экрана монитора.

### 4.5. Настройки отображения календаря

| Параметр | Тип / диапазон | Применяется к |
|---|---|---|
| Шрифт | один из установленных в ОС | ко всем текстам |
| Размер текста | положительное число | ко всем текстам |
| Цвет: название месяца | `Red` / `Green` / `Blue` | только к строке месяца |
| Цвет: названия дней недели | `Red` / `Green` / `Blue` | только к строке дней недели |
| Цвет: дни месяца | `Red` / `Green` / `Blue` | к ячейкам дней |
| Цвет текущего дня | опц., `Red` / `Green` / `Blue` | переопределяет цвет для «сегодня» |
| Цвет выходных дней | опц., `Red` / `Green` / `Blue` | переопределяет для Sa/Su текущего месяца |
| Дни не из текущего месяца | `Show` / `Hide` / `Opacity 0–100` | отображение соседних дней в таблице |
| Расположение подписей | `Top` / `Bottom` | где рисуются строка месяца и строка дней недели относительно блока дней |

Цвета заданы жёстким набором из трёх (`Red`, `Green`, `Blue`); произвольный цветовой пикер в рамках
данного ТЗ **не требуется**. Палитра конкретных значений фиксируется в SPECIFICATION.md.

Приоритет цвета для ячейки дня: текущий день > выходной > базовый.

### 4.6. Превью календаря

В разделе настроек отображается превью календаря **в натуральную величину** на фоне вырезанного
кусока изображения рабочего стола выбранного монитора. Превью обновляется при изменении любой
настройки отображения. Размер фонового фрагмента берётся из расчётного размера прямоугольника
календаря с разумным запасом по периметру.

### 4.7. Общие настройки

- **Чекбокс «в автозагрузке»**: отражает, находится ли приложение в списке автозагрузки ОС.
  Установка галочки — добавляет запись (с ключом `-auto`), снятие — удаляет. Конкретные механизмы
  автозапуска (Windows: реестр `Run`/планировщик/Startup-папка; Linux: `*.desktop` в
  `~/.config/autostart`) — в SPECIFICATION.md.
- **Кнопка «Установить календарь»**: немедленно применяет текущие настройки к рабочему столу
  выбранного монитора, не дожидаясь следующего дня.
- **Кнопка «Убрать календарь»**: возвращает на рабочий стол выбранного монитора оригинальное
  изображение (без календаря).
- В любой момент времени показывается ровно одна из этих двух кнопок, отражая фактическое текущее
  состояние (определяется динамически по тому, что сейчас стоит на рабочем столе — см. §4.8).

### 4.8. Сохранение состояния и сохранность оригинала

- Настройки сохраняются при каждом изменении (debounce, см. SPECIFICATION.md) и восстанавливаются
  при запуске. Хранилище — диск в каталоге приложения/данных пользователя (реестр на Windows для
  настроек **не** используется; реестр задействован только для управления автозапуском).
- **Оригинальное изображение рабочего стола никогда не теряется.** Приложение хранит исходный файл,
  который прислала/прочитала ОС. Календарь рисуется поверх копии; оригинал не модифицируется.
- При каждой перерисовке генерируется новое изображение-результат; предыдущие сгенерированные
  изображения (с календарём) **удаляются**, чтобы не захламлять систему. Число хранимых
  артефактов ограничено (см. SPECIFICATION.md).

### 4.9. Определение текущего состояния рабочего стола

Приложение умеет определять, какое изображение сейчас установлено на выбранном мониторе — с
календарём или оригинальное, — и на основании этого показывает нужную кнопку (§4.7). Механизм
(проверка URI/пути текущих обоев против пути к сгенерированному файлу) — в SPECIFICATION.md.

## 5. Нефункциональные требования

### 5.1. Изображение и геометрия

- Оригинальное изображение может не совпадать по размеру/соотношению сторон с рабочей областью
  монитора; режим растяжения обоев («Fill / Fit / Stretch / Center / Tile» и аналоги в GNOME)
  учитывается при наложении календаря.
- **Независимо от режима растяжения итоговый календарь всегда имеет одинаковый визуальный размер**
  для пользователя. Достигается тем, что приложение работает в координатах пикселей монитора, а не
  координатах исходного файла.
- На разных мониторах — разная картинка рабочего стола; обновляется только рабочий стол выбранного
  монитора (с оговоркой §2.2 для GNOME).
- Количество мониторов берётся из настроек/конфигурации ОС на момент запуска; минимум 2 ожидается,
  но 1 тоже корректно обрабатывается.

### 5.2. UX

- Интерфейс настроек должен быть удобным и интуитивно понятным: сгруппирован по разделам,
  логически связан с превью, без скрытых опций.
- Все разрушительные/внешние действия (применить к рабочему столу, убрать календарь, изменить
  автозапуск) выполняются явно, без подтверждения только если действие очевидно из кнопки.

### 5.3. Производительность и устойчивость

- Silent-режим завершается быстро (порядка секунд, не минут), не оставляет висящих процессов.
- Сбой на одной платформе/DE не должен ронять приложение молча: ведётся лог, код возврата ненулевой.
- Приложение должно корректно работать при отключении/подключении мониторов во время работы (мирная
  обработка случая «выбранный монитор исчез»).

| Аргумент | Поведение |
|---|---|
| *(нет)* | Открыть UI настроек |

## 7. Структура данных настроек (контракт)

Подробная модель — в [`SPECIFICATION.md`](./SPECIFICATION.md), раздел «Модель настроек». Здесь
фиксируются только обязательные поля:

- `TargetMonitorId` (стабильный идентификатор монитора в терминах ОС),
- `Anchor` (одно из 8 значений),
- `MarginPx` (≥ 0),
- `FontFamily`, `FontSize`,
- `ColorMonth`, `ColorWeekday`, `ColorDay`,
- `ColorToday` (nullable), `ColorWeekend` (nullable),
- `OtherMonthMode` (`Show` / `Hide` / `Opacity 0–100`),
- `LabelsPosition` (`Top` / `Bottom`),
- `Autorun` (bool),
- плюс служебные поля: путь к оригиналу, путь к последнему сгенерированному файлу и т.п.

## 8. Критерии приёмки

1. На Windows с 2+ мониторами приложение рисует календарь на выбранном мониторе и не трогает
   остальные; смена дня или ручной «Установить» корректно перерисовывает.
2. На Ubuntu/GNOME приложение запускается, UI работает, превью корректно отображается; установка
   общих обоев с календарём выполняется; `gsettings` отражает смену URI.
3. «Убрать календарь» возвращает исходное изображение на обеих платформах.
4. Включение/выключение автозапуска реально добавляет/удаляет запись (проверяется средствами ОС).
5. Настройки сохраняются между запусками.
6. После N перерисовок в каталоге-хранилище нет «кладбища» старых файлов с календарём.

## 9. За рамками текущей версии (out of scope)

- Сетевые/облачные источники изображений.
- Календарь на несколько месяцев, события, праздники, заметки.
- Произвольная палитра (RGB-пикер); только три предустановленных цвета.
- Локализация названий дней/месяцев на языки, отличные от en-US.
- Поддержка DE, отличных от GNOME, в полной мере (см. §10 — плагинная архитектура).

## 10. Плагинная архитектура Linux-DE (перспектива)

Контракт `IWallpaperService` спроектирован так, чтобы реализация для нового DE подключалась без
изменения ядра. В рамках данной редакции:
- реализован backend GNOME,
- оставлены заглушки `KdeWallpaperService`, `XfceWallpaperService`, `CinnamonWallpaperService`,
  `MateWallpaperService`, выбрасывающие `PlatformNotSupportedException`,
- выбор backend'а на Linux происходит по переменной окружения `XDG_CURRENT_DESKTOP`.
